All In One Save Kit: Reference

Version 1.0 · Rare Geometry

This Reference explains how each part of All In One Save Kit works: the save tree and files, what can be saved, world persistence in depth, reliability and recovery, file options, the save menu's options, the editor tools, performance and logging. For step-by-step tasks, see the Guide; for the C# API, the API Reference.

Settings in bold, such as Save Version, are fields on the settings asset AllInOneSaveKitSettings. To change one, select the asset in the Project window; most are on its Basics tab, the rest under Advanced.

Core concepts #

The save tree #

Everything the kit saves goes into one structure, the save tree. A save file is a small envelope around it:

  • a header: the save format, your game's save version, the game version, the kit version, the time of the save in UTC, a checksum and how the file is packed;
  • the slot info the menu shows: name, playtime, location, game version and summary lines;
  • the data: one section per category, plus a players section in co-op games.

In memory, the data part is SaveKit.Data. Your plain values go there, and the Saveable objects in your scenes write their state there when a save gathers it. A save copies the data into the file; a load replaces it. The menu, the Save Inspector, Diagnostics and recovery all read this same structure.

Files: slots, the global file, autosaves and the quicksave #

File Default name What it holds
Manual slots slot_01.save to slot_10.save One playthrough each. 10 slots by default, adjustable from 1 to 99.
The global file global.save The Global categories, such as Settings. One file for the whole game.
Autosaves autosave_1.save to autosave_3.save Each autosave overwrites the oldest of these files, so an autosave never replaces the newest one. 3 by default, adjustable from 1 to 10.
The quicksave quicksave.save One extra slot for a quick-save key. Off by default.

Slot files, autosaves and the quicksave hold the Slot categories. The global file holds the Global categories. Loading a slot never touches the global file, so a player's settings never go back to an older state.

File names and the save folder #

Saves are kept in a folder inside Application.persistentDataPath. On Windows that is:

%USERPROFILE%\AppData\LocalLow\<Company Name>\<Product Name>\Saves
  • Company Name and Product Name come from Project Settings → Player. The Editor and a Windows build use the same folder.
  • Saves is Save Folder Name. If Profile Folder is set, saves go into that folder inside it (see Profile folders).
  • Once the kit has started, SaveKit.Storage.DescribeLocation() returns the folder. The Save Inspector's Copy folder path button shows it in Explorer.

You can change the names in the settings asset:

Setting Default Notes
Slot File Name Format slot_{0:00} {0} is the slot number; {0:00} gives two digits. A pattern without {0} stops the kit starting with SettingsInvalid (SK153).
Autosave File Name Format autosave_{0} {0} is the autosave number.
Global File Name Base global
Quicksave File Name Base quicksave
File Options → File Extension .save Used by the slots, the autosaves and the quicksave, and by the global file unless it has its own extension (see The global file's own options).

Beside each save you may find these files. Only the real saves end in .save, which is what keeps a Steam Cloud pattern of *.save clean:

File What it is
slot_01.save.tmp A save that was being written when the game stopped
slot_01.save.bak1, .bak2 … Rotating backups, newest first. A .bak0 working copy exists for a moment during each save.
slot_01.save.corrupt-<time> A damaged file, moved aside and kept for support
slot_01.save.thumb.png The slot's thumbnail
slots.index A cache of slot info that makes the menu fast. The kit checks it against each file before using it.

Profile folders: several players on one PC #

Profile Folder puts the saves into a folder inside the save folder, so that two people who share a PC each keep their own saves.

  • A fixed name, such as Player1, is used exactly as written.
  • {profile} is replaced, when the kit starts, by SaveKit.ProfileId, which your game sets at runtime, for example to the player's Steam ID. A Profile Folder of {profile} puts the saves of the Steam user 76561198000000000 into Saves/76561198000000000. The placeholder can also sit inside a longer name, such as Profile_{profile}.

The kit never works out the id itself: it only knows what your game gives it. So with {profile}, the kit has to wait for your game:

  1. In the settings asset, set Profile Folder to {profile} and switch Initialise Automatically off.
  2. When your game knows who is playing, set the id, then start the kit:
SaveKit.ProfileId = playerId;               // for example the player's Steam ID, as a plain number
SaveResult started = SaveKit.Initialise();
if (!started.Success) Debug.LogError(started.ToString());
  • No id, no start. With {profile} in Profile Folder and an empty SaveKit.ProfileId, the kit refuses to start with SettingsInvalid (SK153) rather than mix two players' saves. With Initialise Automatically still on, that shows in the Console as "The kit could not start by itself". When there is no player id, for example in the Editor without Steam running, set a fixed one such as local.
  • What an id may hold. Letters, digits, - and _ are always fine. An id with a character that a folder name cannot hold, such as /, \, : or *, with .., or with spaces at either end, is refused with SK153.
  • When the id is read. The kit reads SaveKit.ProfileId only when it starts, so changing it later does nothing until the next start. To switch players, call SaveKit.Shutdown(), set the new id and call SaveKit.Initialise(); Shutdown also removes your event handlers and co-op hooks, so set them again afterwards. Shutdown keeps the id; a new Play session forgets it.
  • Keeping automatic start on. Unity runs a static method marked [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.AfterAssembliesLoaded)] before the kit starts by itself, so a game that already knows the player at that moment can set SaveKit.ProfileId there instead. SubsystemRegistration is too early, because the kit clears the id at that moment, and BeforeSceneLoad races the kit's own start.
  • In the Save Inspector, outside Play Mode, there is usually no id, so the Inspector lists the save folder itself, with each player's folder inside it. Use Choose folder... to look into one.
  • Decide before release. Adding a profile folder in an update moves the saves to a new folder, so existing saves seem to disappear (SK100).

The Steam Cloud guide uses {profile} with the player's Steam ID.

Categories #

Every saved value belongs to one category. A category decides two things: which file the value goes into, and which saves include it.

  • Slot categories are stored inside each save slot. Progress, inventory, quests and world state belong here.
  • Global categories are stored in the one global file. Player settings belong here.

A new settings asset starts with five categories:

Category Scope Role
Settings Global Player settings
Progress Slot The Default Category: values saved without a category go here
Inventory Slot
Quests Slot
World Slot The World Category: Saveable objects are saved here unless they name another category

You can rename them, add your own and change their scope on the settings asset's Advanced tab, under Categories (In each slot or One shared file), then Apply the categories. The default category and the world category must exist, or the kit refuses to start.

  • Renaming a category in the settings does not rename it inside save files that already exist. Old saves keep the old name until a migration step renames it (see GameUpdates.md).
  • A name the settings do not define is reported once in the Console as CategoryUnknown (SK150), and its values are never saved. Names are case-sensitive.
  • Partial saves. A save or load can include all categories or only some, for example a checkpoint that saves only Progress and World. See Partial saves and loads.
  • Reserved names. No category may be called players: every save keeps each co-op player's own data under that name, beside the categories, so the kit refuses to start with SettingsInvalid (SK153) when one is. Inside a category that holds Saveable objects, the kit uses the keys scenes, persistent, loadedScenes and activeScene itself, so do not store plain values under those keys in such a category.

Save versions #

Every file records the save version it was written with. Save Version is a whole number in the settings asset, 1 by default. Raise it when your saved data changes in a way old saves need help with, and write a small migration step that upgrades version N to N + 1. Migration steps run in order when an old file loads. Saves from a newer version of your game are refused with NewerVersion (SK120) and left untouched.

GameUpdates.md explains when to raise the version, how to write steps, the tree editing helpers, and how to test with old save files.

Saving plain values #

More on this topic is in the Guide.

What can be saved #

Kind Types
Numbers int, long, float, double, decimal, short, byte, sbyte, ushort, uint, ulong
Text and flags string, char, bool
Time and ids DateTime (stored as UTC), TimeSpan, Guid, byte[]
Enums Any enum, stored by name, so reordering or inserting values never breaks a save
Unity values Vector2, Vector3, Vector4, Vector2Int, Vector3Int, Quaternion, Color, Color32, Rect, RectInt, Bounds, BoundsInt
Collections List<T> and T[] of any of the above, or of your own classes
Your own classes and structs Marked [Serializable], saved under Unity's own rules through JsonUtility. If the Inspector shows a value, the kit can save it.
Dictionaries Dictionary<string, T> and Dictionary<int, T>, where T is any type above (see Dictionaries) 
using System;
using System.Collections.Generic;
using AllInOneSaveKit;
using UnityEngine;

public enum Difficulty { Easy, Normal, Hard }

[Serializable]
public class GraphicsOptions
{
    public int quality = 2;
    public bool vsync = true;
}

public class SaveTypesExample : MonoBehaviour
{
    public void Store(GraphicsOptions options)
    {
        SaveKit.Data.Set("difficulty", Difficulty.Hard, "Settings");              // stored as "Hard"
        SaveKit.Data.Set("unlocked", new List<string> { "Forest", "Caves" }, "Progress");
        SaveKit.Data.Set("lastCheckpoint", new Vector3(12f, 0f, -4f), "Progress");
        SaveKit.Data.Set("firstPlayed", DateTime.UtcNow, "Progress");
        SaveKit.Data.Set("graphics", options, "Settings");                         // through JsonUtility
    }

    public void ReadBack()
    {
        Difficulty difficulty = SaveKit.Data.Get("difficulty", Difficulty.Normal, "Settings");
        List<string> unlocked = SaveKit.Data.Get("unlocked", new List<string>(), "Progress");
        Vector3 checkpoint = SaveKit.Data.Get("lastCheckpoint", Vector3.zero, "Progress");
        DateTime firstPlayed = SaveKit.Data.Get("firstPlayed", DateTime.UtcNow, "Progress").ToLocalTime();
        GraphicsOptions graphics = SaveKit.Data.Get("graphics", new GraphicsOptions(), "Settings");
        Debug.Log(difficulty + " " + unlocked.Count + " " + checkpoint + " " + firstPlayed + " " + graphics.quality);
    }
}

Good to know:

  • Enums by name. An enum value that no longer exists, because you removed or renamed it, reads back as the fallback instead of failing the load.
  • Dates are stored as UTC. A DateTime comes back with Kind set to Utc, as the same moment in time. Call .ToLocalTime() before you show it to a player. A date whose Kind is Unspecified is treated as local time when it is saved.
  • Numbers are exact. Floats and doubles read back bit for bit, including NaN, infinity and negative zero. A readable file shows the shortest text that reads back as exactly the same number, so 0.8f is written as 0.8. A few values need more digits: up to nine for a float and seventeen for a double.
  • Numbers look the same in every language. The kit writes numbers in one fixed format, whatever the player's language settings, so a save made on a German PC loads on an English one.
  • Your own classes follow Unity's rules: public fields and [SerializeField] fields of supported types are saved; properties, interfaces and dictionary fields inside the class are not.

Dictionaries #

A Dictionary<string, T> or a Dictionary<int, T> is saved like any other value, as long as T is a type the kit can save:

var kills = new Dictionary<string, int> { { "slime", 12 }, { "bat", 3 } };
SaveKit.Data.Set("kills", kills, "Progress");

Dictionary<string, int> loaded = SaveKit.Data.Get("kills", new Dictionary<string, int>(), "Progress");
  • Get builds a new dictionary from the save each time. When nothing is saved under the key, it returns your fallback.
  • In the file, a dictionary is a JSON object. int keys are written as text, such as "12".
  • A dictionary with other keys, such as an enum, or with values the kit cannot save, is not saved. The Console warns once with InvalidArgument (SK002), and Get returns your fallback. Save such data as two lists instead, or from an ISaveable.
  • A category's writer and reader do the same: SaveKit.Data.Writer("Progress").WriteDictionary("kills", kills) writes it, and SaveKit.Data.Reader("Progress").ReadDictionary<int>("kills") reads it back, or null when there is none. Read int keys back with ReadIntDictionary<TValue>. Writer(category) and Reader(category) also offer WriteList, ReadList, WriteObject and ReadObject, for code that prefers to write a group of values at once.
  • A dictionary field of a script cannot be ticked in the Field Picker, because Unity does not save dictionary fields. Save it from an ISaveable (see Custom scripts).

Threads and the file queue #

  • Capturing and restoring run on the main thread, because Unity's APIs require it.
  • Reading the old file, migrating, merging, serialising, compressing, encrypting and writing run on a background thread for the Async calls and for SaveInBackground and LoadInBackground. The blocking calls do the same work on the calling thread. Profiler markers show which thread each stage ran on.
  • Work for one file runs one item at a time, in the order it was asked for. Two saves fired in a row both finish, and the file holds the second one.

Slots and slot info #

More on this topic is in the Guide.

What a slot records #

Each save records slot info that the menu reads without unpacking the game data:

SlotInfo member What it is
SlotNumber The slot, counting from 1; 0 for an autosave or the quicksave
FileName, Exists The file, and whether there is a save in it
Name SaveKit.SlotName at the time of the save, or Slot N when the game set none
SavedUtc When it was saved, in UTC (use ToLocalTime() to show it)
PlaytimeSeconds Playtime at the time of the save
Location SaveKit.Location at the time of the save
Summary Up to four short lines, such as "Day 12" and "$4,300". The menu shows the first two.
GameVersion, SaveVersion The game's version (Application.version) and save version
ThumbnailFileName The thumbnail file, or empty
BackupCount, FileBytes, Packing Backups on disk, file size, and how the file is packed
IsDamaged, HasValidBackup, RecoveredFromBackup The main file is damaged; a backup can stand in; these details come from a backup copy
IsFromNewerVersion Saved by a newer version of the game, so it cannot be loaded
IsAutosave, IsQuicksave, Status What kind of save it is, and the code from reading it

Set the name, location and summary before you save:

SaveKit.SlotName = "Chapter 3";
SaveKit.Location = "Downtown";
SaveKit.SetSummary("Day 12", "$4,300");

These are kept between saves, and a load sets them from the file. A default name such as Slot 3 is not carried over, so saving that game into slot 5 records Slot 5.

Playtime is counted by the kit while it runs, in unscaled time. SaveKit.Playtime gives the total in Seconds; set IsPaused to stop the clock during menus or cutscenes. A load sets the clock from the save, and NewGame starts it from zero. PlaytimeTracker.Format(seconds) turns a number of seconds into short text such as 2h 15m.

World persistence #

More on this topic is in the Guide.

Parents #

The Position saver records the parent when the parent is a saved object or the scene root, and restores it in the second pass, once every object exists.

  • A scene object under a parent that is not saved keeps the parent it has in the scene.
  • A runtime object under a parent that is not saved, such as a plain "Enemies" container, records that parent's path in the scene and its world pose, so it comes back in the same place. The path assumes sibling names are unique and contain no /. If the parent cannot be found, the object goes to the scene root at the same world position.

Load modes #

World Load Mode in the settings decides how a load treats scenes. SaveKit.World.LoadMode changes it at runtime.

Mode LoadAsync Load (blocking)
Load Saved Scenes (default) Loads the scenes the save was made in, restores each as it loads, sets the active scene, then fires Loaded Restores into the scenes that are loaded now
Restore Into Current Scenes Restores into the scenes that are loaded now Restores into the scenes that are loaded now

When restoring into the scenes that are loaded now, the state of any other saved scene stays in memory and is applied when that scene loads. A file that holds no world data leaves the scenes alone.

Restoring into an open scene cannot bring back a scene object that was destroyed after the save, because the kit has no prefab to make it from: it is skipped with an ObjectNotFound warning. Load Saved Scenes mode reloads the scenes, so everything comes back.

Scene loader hook. For a loading screen, or scenes that are not in Build Settings, set SaveKit.World.SceneLoader to your own ISceneLoader (namespace AllInOneSaveKit.World). Return the AsyncOperation of a SceneManager load and leave allowSceneActivation on:

using AllInOneSaveKit.World;
using UnityEngine;
using UnityEngine.SceneManagement;

public sealed class LoadingScreenSceneLoader : ISceneLoader
{
    public AsyncOperation LoadScene(string scenePath, string sceneName, LoadSceneMode mode)
    {
        // Show your loading screen here.
        string scene = string.IsNullOrEmpty(scenePath) ? sceneName : scenePath;
        return SceneManager.LoadSceneAsync(scene, mode);
    }
}

Return null for a scene you cannot load. Games that load scenes through Addressables load them themselves and use Restore Into Current Scenes, or call SaveKit.World.ApplyScene(scene) once each scene is in.

Component savers #

The Animator, Audio Source, Enabled and NavMesh Agent savers are components beside a Saveable, saved in its entry under their own name like any ISaveable (see World data in the file). Each compiles only when its Unity module is switched on in the Package Manager (Animation, Audio, AI); the Enabled saver always does.

Component Stored members Notes
Animator Saver parameters (one member per float, int or bool parameter), stateHashes, stateTimes, layerWeights Save Parameters and Save States switch the two halves. A state that no longer exists after a game update is left to the controller. The state is played with Animator.Play at the saved normalized time once the Animator is initialised
Audio Source Saver playing, time, volume, pitch Save Playback and Save Volume And Pitch switch the two halves. A time past the clip's end is clamped
Enabled Saver enabled, a list of true or false in the order of Targets Behaviours, Renderers and Colliders; anything else in the list is skipped
NavMesh Agent Saver position, speed, stopped, hasDestination, destination Applied on the agent's next frame with Warp, then SetDestination and isStopped when it is on a NavMesh

State a load hands over before the component can take it is kept, and saved again unchanged if the game saves first; HasPendingRestore says whether it is waiting.

Physics #

Every body whose position a restore puts back is held kinematic for at least one simulated physics step, then released with its saved velocities and sleep state (or with its own settings when the Physics saver is off). Objects that are restored touching each other, such as stacked crates, therefore start from rest instead of bursting apart.

The release happens in FixedUpdate. If Physics.simulationMode is set to Update or Script, the release may not line up with your simulation step.

DontDestroyOnLoad objects #

Saveables under DontDestroyOnLoad, such as a game manager, are saved in a separate persistent section of their category, not with any scene. A load restores them first, before the scenes. Their destruction is not recorded by the Destroyed saver.

The registries #

using AllInOneSaveKit.Editor.Registries;
using AllInOneSaveKit.Settings;
using UnityEditor;

public static class RegisterItemDefinitions
{
    [MenuItem("Tools/My Game/Register Item Definitions")]
    static void Register()
    {
        SaveKitSettings settings = RegistryUpkeep.FindSettings();
        if (settings == null || settings.AssetRegistry == null) return;

Reliability and recovery #

The promise: at every moment during a save, at least one complete, valid copy of it is on disk, and nothing the kit does throws into your game.

Crash-safe writes #

Every save follows the same steps:

  1. Capture the values on the main thread.
  2. Serialise, compress and encrypt (when switched on).
  3. Write slot_01.save.tmp, flush it to the disk, read it back and check it.
  4. Swap it into place with the operating system's atomic replace, then rotate the backups.
  5. Write the thumbnail and the slot cache, then report.

The old save stays intact until the new one is proven good. Anything that goes wrong before the swap leaves every file as it was. A problem tidying the backups after the swap is a warning on a successful save, never a failed one.

Checksums #

Every file carries a CRC-32 checksum of its data, checked on every load. A readable file whose data no longer matches its checksum counts as damaged (see Edited saves for the exceptions). An encrypted file also carries a tamper check (see Encryption).

Rotating backups #

Each save keeps File Options → Backup Count older copies, 2 by default, adjustable from 0 to 5: .bak1 is the newest, .bak2 the one before. A load tries the main file first, then a complete .tmp, then .bak1, .bak2 and so on, and the first valid copy wins. Only damage makes a load move on; a locked file or a missing drive reports itself instead.

Automatic fallback #

File Options → Automatic Fallback is on by default.

  • On: a damaged slot, autosave or quicksave loads from its newest valid backup. The result is a success with the code RecoveredFromBackup (SK102), LoadedFrom and SavedUtc say which copy was used, and the RecoveredFromBackup event fires.
  • Off: loading a damaged save fails with its damage code and moves nothing. The slot info reports IsDamaged and HasValidBackup, and the menu offers Restore backup, which calls SaveKit.RestoreBackup.
  • The global file always falls back, whatever this setting says.
  • Saving over a damaged slot works either way. The save keeps the categories it does not write from the newest valid copy.

With fallback off, a crash during the very first save of a slot leaves only the .tmp file. The slot then reports SK101, and Restore backup puts the .tmp file in place.

Damaged files are kept #

When a load falls back, the damaged main file is renamed .corrupt-<time> and kept for support, never deleted. A file with no valid copy at all gives a clean FileDamaged result (SK101); the game keeps running and nothing is deleted.

Disk full and access denied #

If the disk is full or the folder cannot be written, the save fails with DiskFull (SK110) or AccessDenied (SK111), and every existing save stays byte-for-byte as it was. A save tree nested deeper than 128 levels is refused before anything is written, because it could never be read back.

What the player sees #

In the save menu, a damaged slot shows a Damaged badge. Loading it with fallback on shows "Restored from backup (date)". With fallback off, the card shows a Restore backup button. A slot whose details come from a backup copy shows a Restored badge. See The save and load menu.

Readable JSON and pretty printing #

Saves are readable JSON by default: any text editor opens them, and they are easy to support. With Pretty Print on Automatic, files are indented while you develop and compact in a release build, which is the compact mode for shipping. Whitespace never changes the checksum.

Compression #

GZip makes large saves several times smaller. It is off by default because typical saves are small. Compressed files can no longer be read in a text editor; the Save Inspector still opens them.

Encryption #

Encryption stops players editing saves in a text editor, and its tamper check notices edits.

  • How it works: AES-256 in CBC mode with a random IV for every write, and an HMAC-SHA256 over the header and the encrypted data (encrypt-then-MAC). The keys are derived once, when the kit starts, from Passphrase, Key Salt and Key Iterations with PBKDF2 (SHA-256).
  • A changed byte fails the tamper check (TamperDetected, SK105) and the backup loads. A file written with another passphrase gives EncryptionKeyWrong (SK106).
  • Its limits: the key ships inside your game, so a determined player can dig it out, especially from Mono builds, which are easy to decompile. It is not anti-cheat, and it must never protect passwords, payment details or other personal data. In co-op, the host's save is the authority anyway.
  • Set your own passphrase before release. Diagnostics warns while the default one is set and either the slots or the global file are encrypted. After release, never change Passphrase, Key Salt or Key Iterations, or existing encrypted saves can no longer be opened.
  • Thumbnails are never encrypted.

LimitsAndFAQ.md explains the limits of encryption in more detail.

How the options combine #

Data is compressed first, then encrypted, because encrypted data cannot be compressed. A compressed or encrypted file uses a binary envelope: a short marker, a readable header, then the packed data. The loader tells readable and packed files apart from their first bytes, and the header records which options were used, so any mix loads correctly.

Changing options in an update #

Each file records how it was written, and the loader follows the file, not the settings. You can switch compression or encryption on or off in a game update and old files still load; they are written the new way the next time they are saved. The same goes for giving the global file its own options, or taking them away again (see below). The one thing you must not change after release is the passphrase, salt or iteration count. See GameUpdates.md.

Edited saves: the checksum policy #

A readable save edited by hand no longer matches its checksum.

  • Treat Edits As Damaged (default): in a build, the file counts as damaged and the newest backup loads instead (ChecksumMismatch, SK104). This also catches files that were cut short.
  • Accept With Warning: the file loads, with a warning in the report. Use this for moddable games.
  • The Editor always accepts edited files, with a warning, so you can tweak saves while you test.

The global file's own options #

The global file holds the player's settings. By default it is written with File Options, like the slots. To give it options of its own, tick Write it differently under Shared file on the settings asset's Advanced tab (in code, untick Use Slot Options For Global File) and fill in Global File Options, or tick Different options for the settings file in the wizard's File options step.

  • Global File Options has the same fields as File Options. The global file then uses its own Pretty Print, Compress, Encrypt, Encrypt Slot Info, Backup Count, Checksum Policy and File Extension.
  • Passphrase, Key Salt and Key Iterations always come from File Options, so every file of your game shares one key. The ones in Global File Options are never used.
  • Automatic Fallback makes no difference: the global file always falls back to its newest good backup.
  • An empty File Extension, the default, keeps the slots' extension. Another extension, such as .local, gives the global file its own name, global.local, and its working copies follow it: global.local.tmp, global.local.bak1 and so on. This is how you keep machine-specific settings, such as graphics quality, out of a Steam Cloud pattern of *.save (see SteamCloud.md).
  • An extension the kit cannot use stops it starting with SettingsInvalid (SK153). It needs a dot followed by a few letters, and it cannot be .tmp or start with .bak or .corrupt, which the kit uses for its own copies.
  • Switching after release is safe. When a game update gives the global file its own extension, or takes it away again by going back to the slots' options, the kit looks for the file under both names and loads whichever was written last, so the player keeps their latest settings. The next save writes the new name, and the old file is left where it is. Only those two names are looked at: changing the global file's own extension from one value to another, such as from .local to .cfg, leaves the settings under the old name behind.
  • The Save Inspector lists the global file under its own extension too.

The kit reads these options when it starts.

The settings asset's Inspector #

Select AllInOneSaveKitSettings to edit it. Basics holds the game presets, where saves go, slots, autosave, start-up and Console messages. Advanced holds, each in a section that starts collapsed:

  • File names and the profile folder: Profile folder (see Profile folders), Shared file name, Autosave file names, Quicksave file name.
  • Categories: rename, add or remove categories, choose In each slot or One shared file for each, and pick where values from code and Saveable objects go (those two cannot be removed). Apply the categories applies them as one Undo step; Undo my edits goes back to what the asset holds.
  • Packing, encryption and backups: Indent the text, Compress, Encrypt with Passphrase and Generate, Older copies kept, Use a good copy by itself, A save edited by hand, and under Shared file, Write it differently with its own Indent the text, Compress, Encrypt, Older copies kept and File extension (see The global file's own options). Apply the file options applies them as one Undo step.
  • Game updates: Save version and Find migration steps by itself (see Save versions).
  • World objects: When a save is loaded (see Load modes) and the three registries.
  • Scene scan: lists objects in the open scenes that look stateful: a Rigidbody, a trigger collider (pickups, checkpoints), a script with fields named like state such as isOpen or health, a script that implements ISaveable, or a renderer that starts hidden. Tick the ones to keep; each gets a Saveable with the state-like fields already ticked.

The Play Mode toast #

In the Editor, a short note at the top of the Game view says what each save or load did, for example "Saved Slot 1: 12 objects, 3 values" or "Loaded Slot 1: 11 restored, 1 skipped, Chest_02 not found (SK130). Click for details". A load of plain values only says how many values came back. A failed call names its code. Clicking the note opens the Save Inspector on that report. It is on by default; Tools → All In One Save Kit → Play Mode Toasts switches it off and on, per user. It is never added in batch mode and does not exist in builds.

Save Inspector #

Tools → All In One Save Kit → Save Inspector shows what is inside any save.

  • The list shows every save in the game's save folder, including a global file with its own extension, with a status badge (OK, Damaged, Wrong key, Missing, Unreadable, Newer version, Older version), Encrypted and Compressed badges, and a line with its backups, size, save version and local time. A damaged save with a good backup says so. Choose folder... looks at another folder, such as a copy of a player's save folder or one player's profile folder; Game's folder goes back. Refresh lists again. With {profile} in Profile Folder, the game's folder is the save folder itself until SaveKit.ProfileId is set; each player's saves are in a folder inside it, which Choose folder... opens.
  • The tree opens a save as file → category → scene → object → value. Scenes show their path and objects their saved name. A saved transform reads as one row, such as "Position (0, 0.5, 2) Rotation (0°, 90°, 0°) Scale (1, 1, 1)", and opens to the raw values; the playtime shows its clock time too. Pick a backup, the temporary file or a damaged copy from the copy menu to look at it instead of the main file. Encrypted saves open with your project's key, and edited readable saves open with a warning.
  • Search finds keys and values, ignoring case; matches stay visible and are highlighted. Expand all and Collapse all help with large saves.
  • Highlight: clicking an object row selects and pings that object when it is in an open scene.
  • Live view: in Play Mode, the Live view entry shows what a save would write right now, without writing anything. Auto refresh rebuilds it by itself, at most twice a second; Export... writes it as readable JSON.
  • Actions: Import... copies a player's save file into the folder for debugging; replacing a save that is there asks first and keeps the old one as a backup. Export readable... writes an indented, decrypted, unpacked copy. Restore backup puts the newest good backup of a damaged save back in place. Delete removes a save with its backups and thumbnail. Copy folder path copies the folder's path, to paste into Explorer's address bar. Right-click a file or a row for more, such as copying a value, a file's path or an object id.
  • Recent saves and loads lists the reports of the current Play session with the time of each (see Logging and reports).

The Saveable inspector #

The Saveable's inspector has these parts:

  • The summary: one sentence at the top that says what it saves, such as "Saves position, active state and 2 fields: Is Open, Gold."
  • What to save: the built-in savers Position, Active state, Destroyed with When it comes back, and Movement (physics), each with a one-line explanation.
  • Values from your scripts (the Field Picker): one group per component, with a ticked count, a Ticked only filter, greyed fields with their reasons, and a list of broken ticks with Untick buttons. Select a single object to use it.
  • The Start warning: when the script's own Start method may set a ticked field, a warning says so, because the kit restores saved values before Start runs (see Load order). It comes from a quick look through the script's text, so it says "may"; Dismiss hides it for that field in this project and Select script shows the script in the Project window.
  • Advanced: id and category, collapsed by default: the object's Id (read-only) with a New id button, which asks first because saves made so far no longer find the object (on a prefab asset, the Prefab id; in Play Mode, runtime objects show their Runtime id), and the Category, with "World category (World)" as the default and every category from the settings.

Performance #

Background work #

  • On the main thread, a save only captures: it reads the Saveables and copies the values. Reading the old file, migrating, merging, serialising, compressing, encrypting, writing and verifying, and writing the thumbnail and the slot cache, run on a background thread for every Async call and for SaveInBackground.
  • A load reads, verifies, unpacks and migrates on a background thread, and only puts the values into the game on the main thread. This holds for every Async load and for LoadInBackground.
  • The blocking calls (Save, Load, SaveGlobal, LoadGlobal, Autosave, Quicksave, LoadQuicksave, LoadNewestAutosave and RestoreBackup) do all of this on the calling thread. Use them where waiting is the point, such as when the game quits. The kit's own quit autosave is one of them; its timed and scene-change autosaves run in the background.
  • Reading slot info for a menu (GetSlotInfo, GetSlotInfos, GetAutosaveInfos) reads files on the calling thread, but only once per change: the result is kept in slots.index until the file changes.

Profiler markers #

Each stage of a save and a load shows up in Unity's Profiler under its own marker, on the thread it ran on. Open Window → Analysis → Profiler, record while the game saves or loads, and find the markers in the CPU Usage module's Timeline view.

Marker Stage
AIOSK.Capture Gathering the values and the world before a save, on the main thread
AIOSK.Serialize Turning the save tree into JSON text
AIOSK.Compress GZip compression of the data
AIOSK.Encrypt Encrypting the data and signing the file
AIOSK.Write Every disk write: the temporary file, the swap into place, the backups, the thumbnail and the slot cache
AIOSK.Verify Reading the temporary file back and checking it before it is swapped into place
AIOSK.Read Every disk read
AIOSK.Decrypt Checking the signature and decrypting the data
AIOSK.Decompress Unpacking compressed data
AIOSK.Parse Turning JSON text into the save tree and checking its checksum
AIOSK.Migrate Running migration steps on an old save
AIOSK.Restore Putting the loaded values back into the game and the world, on the main thread
  • AIOSK.Capture and AIOSK.Restore always run on the main thread. With the Async and callback calls, the other ten run on a background thread, so the main thread shows no AIOSK.Write or AIOSK.Read during a background save. With the blocking calls they run on the calling thread.
  • The markers cost next to nothing while the Profiler is not recording.
  • The names are also constants in SaveProfilerMarkers (namespace AllInOneSaveKit.Diagnostics), such as SaveProfilerMarkers.Write, for code that reads the markers with Unity's ProfilerRecorder, for example in a performance test.

Where the time goes #

Main-thread time grows with the number of Saveables and ticked fields. Objects whose pose has not changed since the last save cost less, because the kit reuses their saved position. Every report records how long each stage took (CaptureMilliseconds, SerializeMilliseconds, CompressMilliseconds, EncryptMilliseconds, StorageMilliseconds, RestoreMilliseconds and TotalMilliseconds), with the file size and object counts. The Console's one-line report gives the total for every save and load, and at the Verbose log level the time of each stage too. The Save Inspector's report list shows them all.

Compact files for release #

With Pretty Print on Automatic, release builds write compact JSON, without indentation. For large worlds, switch on Compress: JSON usually shrinks several times.

Measured benchmarks #

The kit is built to these targets, measured in a release Windows build:

Test Target
P1: save 1,000 objects with 5 fields each Main-thread capture 8 ms or less; the whole save 100 ms or less
P2: save 10,000 objects Main-thread capture 60 ms or less; compression makes the file at least 3 times smaller
P3: restore 1,000 objects into a loaded scene 50 ms or less on the main thread
P4: a background save No disk work on the main thread, confirmed by the Profiler markers

Results for 1.0.0. The machine: AMD Ryzen 7 5700X3D (8 cores, 16 threads), 32 GB RAM, AMD Radeon RX 9060 XT, Windows 11 (10.0.26200), Unity 6000.3.24f1, Built-in render pipeline, release Windows players. Every run is the worst case: every object is changed before every save, so nothing can be skipped. Times are medians of 30 measured saves or loads (P1 and P3) or 40 (P2) after warm-up runs, and a test passes when its median meets the target.

IL2CPP (the backend to ship with), two runs of the 1.0.0 code, given in run order:

P1: whole save, capture to file on disk (SaveAsync awaited) median 59.34 / 62.79 ms 100 ms Pass
P2: main-thread capture, 10,000 objects median 58.87 / 58.27 ms (90th percentile 77.5 / 79.4 ms) 60 ms Pass on the median in both runs

Single large captures can take longer than 60 ms. The P2 median meets the target, but only just, and the 90th percentile does not: 77 to 79 ms. So at least one capture of 10,000 changed objects in ten takes longer than the target. Earlier builds during development measured P2 medians of 52.9 to 54.7 ms; the 1.0.0 numbers above are the ones that describe the shipped code. A development build is slower and is not the target configuration.

Mono (release), one run of the 1.0.0 code:

Test Measured Target Result
P1: main-thread capture median 6.664 ms (90th percentile 7.63 ms) 8 ms Pass
P1: whole save median 70.46 ms 100 ms Pass
P2: main-thread capture, 10,000 objects median 66.60 ms 60 ms Fail

Mono misses the P2 capture target. On Mono, capturing 10,000 changed objects in one go takes a median of 66.60 ms on this machine, over the 60 ms target. The capture makes a call into the engine and some small allocations for every object, and both cost more under Mono than under IL2CPP. Every other target holds on Mono. For release builds of games with very large worlds, build with IL2CPP (Player Settings → Other Settings → Scripting Backend).

Autosave and quicksave thumbnails. An autosave's or quicksave's own picture adds a median of 2.0 ms on the main thread (90th percentile 2.2 ms, slowest 2.9 ms; 20 pictures of a scene with a light and 100 cubes, release IL2CPP player run with a graphics device). The PNG, about 2.3 ms more, is made on the save's background thread.

These are measurements on one machine, not guarantees: a slower CPU, a larger world or more fields per object take longer. The capture, and for an autosave or quicksave its picture, are the only parts of a save that hold the main thread; the capture grows with the number of saved objects and fields; the Profiler markers in Profiler markers show where the time goes in your own game.

Logging and reports #

Log levels #

Every line the kit writes to the Console starts with [All In One Save Kit], followed by the SK code when there is one.

Level What reaches the Console
Off Nothing
Errors Failures only
Warnings (default) Failures and warnings, including the warnings in each save and load report, and a one-line report for every save and load while Report To Console is on
Verbose Everything: the one-line report for every save and load, with the time of each stage, and information lines such as where the saves are kept

Set Log Level in the settings asset; it applies when the kit starts. To change it while the game runs, set SaveLog.Level (namespace AllInOneSaveKit.Diagnostics). Use Verbose while you investigate a problem, and Warnings for release.

The one-line report #

With Report To Console on (under Diagnostics in the settings asset; off by default, so the Console stays quiet), every save and load prints one line at the Warnings and Verbose levels:

[All In One Save Kit] Save slot_01.save: 12.4 ms, 5 categories, 214 values, 40 objects (3 spawned), 5321 bytes, 0 warnings
[All In One Save Kit] Load slot_01.save: 9.8 ms, 5 categories, 214 values, 40 objects restored, 1 skipped, 5321 bytes, read from Backup1, 2 warnings
  • A save or load that failed says so after the file name, for example Load slot_01.save failed with SK101 FileDamaged: ....
  • "read from Backup1" means the load fell back to a backup; "skipped" counts saved objects that are no longer in the scene.
  • At Verbose, the line also gives the time of each stage after a |: capture, serialize, compress, encrypt, storage and restore, and how many migration steps ran.
  • Tick Report To Console to get the line at Warnings. The warnings themselves are always printed, and Verbose always prints the line; every report is also in the Save Inspector's Recent saves and loads. To change it while the game runs, set SaveLog.ReportToConsole.

The kit does not print every failed call. A call refused before it starts, such as one that returns SlotOutOfRange, only appears in the result, so always check Success in your own code. The kit's own autosaves do print their failures.

The report #

Every save and load produces a SaveReport, available as result.Report and in the Saved and Loaded events:

Member What it holds
Operation, FileName What was done, to which file
CaptureMilliseconds, SerializeMilliseconds, CompressMilliseconds, EncryptMilliseconds, StorageMilliseconds, RestoreMilliseconds, TotalMilliseconds Timings
FileBytes, UnpackedBytes Size on disk, and size of the data once unpacked
CategoryCount, ValueCount Categories and values
ObjectCount, SpawnedCount, RestoredCount, DestroyedCount World objects saved or restored, runtime objects written or re-created, destroyed-list entries applied
SkippedCount, SkippedObjects Saved objects that are no longer in the scene, as "name (id)"
LoadedFrom, Packing, MigrationsRun Which copy was read, how the file was packed, which migration steps ran
Warnings Each with its own code and detail

report.ToString() gives a one-line summary. Every finished report is also kept, whatever the log level, in SaveLog.RecentReports (the last 20 of the Play session), and SaveLog.ReportAdded fires for each one. The Save Inspector lists them under Recent saves and loads.

using AllInOneSaveKit.Diagnostics;
using UnityEngine;

public class SaveDebugLog : MonoBehaviour
{
    void Awake()
    {
        SaveLog.Level = SaveLogLevel.Verbose;
        SaveLog.ReportAdded += report => Debug.Log("Save report: " + report);
    }
}

SaveLog.ReportAdded handlers are dropped at the start of every Play session.
