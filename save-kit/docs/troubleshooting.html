Troubleshooting

All In One Save Kit by Romano Assets never throws an exception into your game. Every save, load and delete returns a result instead. When there is something to report, the result carries a code such as SK101, a plain-English message and a link to this guide. This guide has one entry for each code. Each entry explains what the code means, what usually causes it and how to fix it.

If the kit's menus are missing after import #

What it means: The save menu, the editor tools' windows (the Start window, the Setup Wizard, the Save Inspector and Diagnostics) and the demos are built on two Unity packages, Unity UI (com.unity.ugui) and TextMesh Pro, and one of them is missing from the project. TextMesh Pro is part of Unity UI from Unity 2023.2 and the separate com.unity.textmeshpro package in Unity 2022.3. The kit still imports without compile errors: the runtime (SaveKit) and the core editor services (saved ids for Saveables, the registries and their Registries commands, and the migration link file for builds) compile and keep working. The menu, the windows and the demos wait for the package, so Tools → All In One Save Kit shows only Required Packages and the Registries commands. The Console shows a warning once per editor session that starts [All In One Save Kit] The kit's save menu, editor tool windows and demos need and names the package, and says how to install it; Tools → All In One Save Kit → Required Packages shows the same steps. A player build stops with the same message until the package is in.

Likely cause: The project was not made from one of Unity's templates, or the package was removed. Projects made from Unity's templates already have both. The Asset Store installs them together with the kit only when the publisher declares them as dependencies of the package.

Fix: Click Open Package Manager in the dialog (or choose Tools → All In One Save Kit → Required Packages, or open Window → Package Manager yourself). Choose Unity Registry at the top left, select the package and click Install. The kit never installs packages itself. When Unity has finished compiling, the kit's other commands appear and the Start window opens.

How codes appear #

Every SaveKit call returns a result. Saves and deletes return a SaveResult and loads return a LoadResult. Both have these parts:

  • Success: whether you got what you asked for. Only two outcomes count as success: a result with no code (SK000, which has no entry here) and SK102, a load that was rescued from a backup.
  • Code: a SaveErrorCode, written as SK plus three digits. Code numbers never change between versions, so a code quoted in an old support email still means the same thing.
  • Message: one plain sentence. Details such as the file name follow in brackets.
  • DocumentationLink: the path to this file plus the entry's anchor, for example AllInOneSaveKit/Documentation/Troubleshooting.md#sk101.
  • Report: counts, timings, bytes and Warnings. A call that succeeded can still carry warnings, and each warning has its own code.

result.ToString() puts the code, message and link on one line, ready for a log:

LoadResult loaded = await SaveKit.LoadAsync(slot: 1);
if (!loaded.Success) Debug.LogWarning(loaded.ToString());
// SK120 This save was written by a newer version of the game. ... See AllInOneSaveKit/Documentation/Troubleshooting.md#sk120

The first digit groups the codes by area:

  • SK0xx: general problems
  • SK10x: save files
  • SK11x: disk and storage
  • SK12x: game updates
  • SK13x: world persistence
  • SK14x: co-op
  • SK15x: slots and settings

Reading the Console report #

Every line the kit writes to the Console starts with [All In One Save Kit], followed by the code when there is one. A warning from a save or load looks like this:

[All In One Save Kit] SK130 Chest_03 (8c1f...): it is no longer in the scene, so its saved state was skipped.

Every save and load also prints a one-line report, while Report To Console is ticked (it is off by default) and Log Level is Warnings or Verbose:

[All In One Save Kit] Save slot_01.save: 12.4 ms, 5 categories, 214 values, 40 objects (3 spawned), 5321 bytes, 0 warnings
[All In One Save Kit] Load slot_01.save: 9.8 ms, 5 categories, 214 values, 40 objects restored, 1 skipped, 5321 bytes, read from Backup1, 2 warnings

At Verbose the line also gives the time of each stage, after a |: capture, serialize, compress, encrypt, storage and restore. A save or load that failed says so straight after the file name, for example Load slot_01.save failed with SK101 FileDamaged. At Errors and Off no report line is printed. Tick Report To Console (under Diagnostics in the settings asset, or set SaveLog.ReportToConsole while the game runs) to get the line; the warnings themselves are always printed.

  • "read from Backup1" means the load fell back to a backup (SK102).
  • "skipped" counts saved objects that are no longer in the scene (SK130). Their names are listed in Report.SkippedObjects.

The kit does not print every failed call. SK151, for example, only appears in the result, so always check Success in your own code. The kit's own autosaves do print their failures.

Logging levels. Set Log Level in the settings asset, under Diagnostics. The choices are Off, Errors, Warnings (the default) and Verbose. The kit applies the level when SaveKit.Initialise runs. To change it while the game is running, set SaveLog.Level (in the namespace AllInOneSaveKit.Diagnostics). Use Verbose while you investigate a problem, and Warnings for release.

Settings in bold, such as Save Version, are fields on the settings asset AllInOneSaveKitSettings. The Start window (Create) or the Setup Wizard creates this asset in a Resources folder. To change a setting, select the asset in the Project window.

Where the files are. On Windows, saves are kept in %USERPROFILE%\AppData\LocalLow\<Company Name>\<Product Name>\Saves. That is Application.persistentDataPath, then Save Folder Name, then Profile Folder if one is set, with {profile} replaced by SaveKit.ProfileId. Slot 1 is saved as slot_01.save. Next to it you may find these files:

  • slot_01.save.tmp: a save that was still being written.
  • slot_01.save.bak1 and slot_01.save.bak2: backups.
  • slot_01.save.corrupt-<time>: a damaged copy, kept for support.

Tools → All In One Save Kit → Save Inspector lists all of these files, opens any of them and opens the save folder.

Your players' saves are protected by design:

  • A save is first written to a temporary file. The kit reads that file back to check it, and only then swaps it into place. A save that fails or is cut short leaves the previous save exactly as it was.
  • A load tries the main file first. If that fails, it tries a complete temporary file, then each backup, newest first.
  • A damaged file is renamed and kept. It is never deleted.
  • The automatic fallback to a backup is on by default. If you turn off File Options → Automatic Fallback, a damaged main file makes the load fail with its damage code (SK101, SK103 to SK107), and nothing is moved aside. The player can then choose to restore the newest valid backup with SaveKit.RestoreBackup(slot).
  • A file the game cannot read safely, such as a save from a newer version, is left untouched.

SK001: Unknown #

What it means: Something failed that the kit could not name more precisely. The detail in brackets says what the kit was doing. As a warning inside a report, SK001 means the rest of the save or load still went ahead.

Likely cause: Usually an exception from game code the kit calls, such as ISaveable.CaptureState, RestoreState or your ISpawnHandler. Also: a disk error Windows did not explain, a thumbnail that could not be encoded, or a saved scene that took longer than SaveKit.World.SceneLoadTimeoutSeconds (120 by default) to load. "Stopped unexpectedly" points to a kit bug.

Fix: Read the Console error and its stack trace. If it points into your script, fix that method. The kit caught the exception, so the game kept running. For a scene timeout, check your ISceneLoader and allowSceneActivation. Send stack traces inside AllInOneSaveKit to support. A save that stops part-way never replaces the file on disk.

SK002: InvalidArgument #

What it means: The kit was given a value it cannot use, so it refused the call. Nothing was written.

Likely cause: One of these:

  • SaveKit.Quicksave() was called while Quicksave Enabled is off.
  • Encryption is on, but File Options → Passphrase is empty.
  • The save data is nested more than 128 levels deep.
  • SaveKit.LoadScene was given an empty scene name, or SaveKit.UnloadScene was asked to unload the only loaded scene.
  • SaveKit.RestoreBackup was called on a slot whose main file reads correctly. The file was left as it was.
  • SaveKit.Load, LoadAsync, Delete, RestoreBackup or RestoreBackupAsync was given a SlotInfo that names no file of this game: no slot in range, autosave or quicksave, or null. A SlotInfo you build yourself, or one for the global file, is refused, so these calls can never reach a file the kit does not own.

In a save report, SK002 usually means the texture given to SaveKit.SetNextThumbnail is not readable. The save itself still succeeded. In the Console, SK002 can also mean that SaveKit.Data.Set or SaveWriter.Write was given a Dictionary it cannot save: only string or int keys, with values of a supported type, are saved. Such a dictionary is stored as no value, and Get returns your fallback.

Fix: The detail in brackets names the value. Turn on Quicksave Enabled or stop calling Quicksave(). Set a passphrase. Flatten very deep data, or store it through ISaveable. Save a dictionary with other keys or values as separate lists, or with WriteAssets for asset references. For thumbnails, pass a texture from ScreenCapture.CaptureScreenshotAsTexture(), or tick Read/Write in the texture's import settings. For a SlotInfo, pass one that SaveKit.GetSlotInfo, GetAutosaveInfos or GetQuicksaveInfo returned.

SK003: Busy #

What it means: A save or load could not start because another one on the same file did not finish in time. Nothing was written.

Likely cause: The kit itself never returns SK003 in 1.0. Saves and loads of the same file wait in a queue and run in order, however long that takes. Only a custom ISaveStorage of your own could return this code.

Fix: If your storage returns SK003, await the earlier call, then try again. If the game freezes while saving instead, look for code on the main thread that calls .Wait() or reads .Result on a SaveKit task. The task needs the main thread to finish, so the game waits forever. Use the blocking SaveKit.Save or SaveKit.Load there instead. If you see SK003 without custom storage, it is a bug in the kit, so please report it.

SK004: Cancelled #

What it means: A save or load was stopped before it finished.

Likely cause: The 1.0 API has no way to cancel a call, so the kit itself never returns SK004. Only a custom ISaveStorage of your own could return it. If SaveKit.Shutdown() or a second SaveKit.Initialise() interrupts a save or load, the result is SK005, not SK004.

Fix: If your storage returns SK004, run the call again once the storage is ready. If you see SK004 without custom storage, please report it as a bug in the kit. A stopped save never replaces the file already on disk, because the new file only goes into place after it has been written in full and checked.

SK005: NotInitialised #

What it means: The kit was used before it had settings and a save folder, or it was stopped or restarted mid-call. Nothing was read or written.

Likely cause: One of these:

  • The settings have not been created yet (the Start window's Create, or the Setup Wizard), or AllInOneSaveKitSettings is not inside a Resources folder.
  • Initialise Automatically is switched off in the settings asset, and SaveKit.Initialise() was never called, or it failed and nobody checked the result.
  • The kit tried to start by itself and could not. The Console then shows an error that starts "The kit could not start by itself" and names the problem.
  • SaveKit.Shutdown() or a second Initialise() ran during a save or load, including from a Saving or Loading event handler.

If domain reload is turned off (Enter Play Mode Options), the kit still resets every time you press Play.

Fix: Open Tools → All In One Save Kit → Start and click Create next to No settings yet, or run the Setup Wizard. With Initialise Automatically on (the default, under Start-up in the settings asset), the kit starts by itself just before the first scene loads, in the Editor and in builds, and nothing else is needed. With it off, call SaveKit.Initialise() once on the main thread before the first save or load, for example in Awake in your first scene, in every Play session. Either way, check the Console or result.Success: the code explains any problem with the settings.

SK100: FileNotFound #

What it means: There is no main file, temporary file or backup with that name. This is normal on a first run. Nothing was changed.

Likely cause: SaveKit.LoadGlobal(), LoadNewestAutosave() or LoadQuicksave() ran before that file was ever saved. If saves that used to load have disappeared, the kit is looking somewhere else. That happens when Save Folder Name, Profile Folder, a file name pattern or File Options → File Extension changed. It also happens when Company Name or Product Name changed in Player Settings, because that moves Application.persistentDataPath.

Fix: On a first run, treat SK100 as "start from defaults". Otherwise, change the settings back to the values the saves were made with. The old files are still on disk under the old folder or name. The Save Inspector can open the save folder so you can see what is there.

SK101: FileDamaged #

What it means: The save could not be read, and neither could the temporary file or any backup. Nothing was deleted, and the game keeps running.

Likely cause: The copies are damaged in different ways: empty, cut short or not valid JSON. If they all fail the same way, you get that code instead. This usually follows a power cut or a faulty drive. SK101 also appears when:

  • A save's new file did not read back correctly, so it was not swapped in.
  • A save of only some categories found the old file unreadable, so it wrote nothing.
  • SaveKit.RestoreBackup found no valid backup.
  • Automatic Fallback is off and the main file of a slot, an autosave or the quicksave is missing or unreadable. A valid backup may well exist: the load does not use it on its own. With fallback off, a crash during the very first save of a slot, before the new file was swapped in, leaves only slot_01.save.tmp, and the load reports that as SK101 too. The global file always falls back, whatever the setting.

Fix: The report's warnings list every copy the kit tried, with its code. With Automatic Fallback off, check SaveKit.GetSlotInfo(slot).HasValidBackup: when it is true, SaveKit.RestoreBackup(slot) puts the newest valid backup (or the .tmp file) in place and the slot loads again. The save menu offers this as Restore backup. Otherwise, import the player's file into the Save Inspector to look inside. Tell the player kindly that this save can't be loaded, and offer another slot, an autosave or a new game. After SaveKit.NewGame(), saving to that slot replaces the damaged file. Keep File Options → Backup Count at 1 or more.

SK102: RecoveredFromBackup #

What it means: Success. The main file could not be used, so the kit loaded the newest good copy. Success and RecoveredFromBackup are both true. LoadedFrom names the copy (Temporary, Backup1, Backup2 or OlderBackup), and SavedUtc says when that copy was saved. Temporary is a save that was being written when the game stopped, so it is the newest. SaveKit.RestoreBackup also returns SK102 when it has put a backup back.

Likely cause: The main file failed one of the kit's checks, for example SK104 after a hand edit, or after a crash cut the file short. The report's warnings give the reason. In a save report, SK102 means the save kept the other categories from a backup.

Fix: No action is required. The damaged file was kept as <name>.corrupt-<time>, and the next save writes a new main file. Tell the player briefly, for example "Restored from backup (12 Oct, 18:41)", using SavedUtc.ToLocalTime(). Any progress made after that backup may be missing. Handle SaveEvents.RecoveredFromBackup to show the message from one place.

SK103: UnsupportedFormat #

What it means: This kit version cannot read the file. Either the kit did not write it, or it uses a newer file format. The kit treats it like damage and tries the backups.

Likely cause: One of these:

  • Another tool writes files with the same name and extension into the same folder.
  • A file was renamed to .save by hand.
  • A later kit version wrote the save in a newer format, and an older build is reading it.

Fix: Give the kit its own folder with Save Folder Name, and set it before you ship, because changing it later hides existing saves. Use the same or a newer kit version in every build that reads the same saves. If a backup loaded, you get SK102 and the unreadable file is kept as .corrupt-<time>. If no copy could be read, or Automatic Fallback is off, nothing was touched.

SK104: ChecksumMismatch #

What it means: The data no longer matches the checksum in the file's header, so the file was edited or cut short after it was written. Changes to spacing only do not count. A readable file with no checksum at all is reported the same way.

Likely cause: Someone edited a readable save in a text editor, or the file was cut short. In a build, the default File Options → Checksum Policy (Treat Edits As Damaged) falls back to a backup, which gives SK102. You get SK104 when no copy can be used, or when Automatic Fallback is off. In the Editor, edited files always load, with SK104 as a warning, so you can tweak saves while testing.

Fix: To let players edit saves, for example for modding, set Checksum Policy to Accept With Warning. Otherwise nothing is needed. The backup loaded, and the edited file was kept as .corrupt-<time>. If every copy fails the check, nothing is touched. Open the file in the Save Inspector to see what it holds.

SK105: TamperDetected #

What it means: An encrypted save was written with the current passphrase, but it failed its tamper check, so its contents changed after it was written. The kit treats it as damaged and tries the backups.

Likely cause: A player changed the encrypted file with a hex editor or a save-editing tool, or a faulty drive or another program changed bytes on disk. Even one changed byte causes this.

Fix: Usually nothing is needed. The newest good backup loads (SK102), and the changed file is kept as .corrupt-<time>. If every copy fails, or Automatic Fallback is off, nothing is touched. If many players report this code, check whether another program writes to the save folder. Remember that encryption only stops casual editing. The key ships inside the game, so encryption is not anti-cheat. In co-op, the host's save is the one that counts.

SK106: EncryptionKeyWrong #

What it means: An encrypted save was written with a different key from the one in the settings, so it cannot be opened. When every copy fails this way, nothing is moved or deleted.

Likely cause: One of these:

  • File Options → Passphrase, Key Salt or Key Iterations changed after the save was written.
  • The settings asset was recreated. The Setup Wizard gives each new asset its own random salt.
  • Passphrase is empty.
  • The file came from another game or project.

Fix: Put back the exact passphrase, salt and iteration count the save was written with, and the file loads again. Choose these values once, before release. Diagnostics warns while the default passphrase is still set. Keep the values in version control and never change them. Turning Encrypt off later is safe: each file records how it was packed, so old encrypted files still open as long as the key stays the same.

SK107: CompressionFailed #

What it means: The compressed (GZip) part of a save could not be unpacked. The kit treats it as damaged and tries the backups.

Likely cause: The packed bytes of a compressed save were damaged on disk, for example by a faulty drive or by another program that changed the file. Encrypted files fail their tamper check (SK105) before they reach this point, so SK107 mostly appears for files that are compressed but not encrypted.

Fix: Usually nothing is needed. The newest good backup loads (SK102), and the damaged file is kept as .corrupt-<time>. If no copy can be read, or Automatic Fallback is off, nothing is touched. Turning File Options → Compress on or off in an update is safe and never causes this code. Each file records how it was packed, and the kit reads it that way.

SK110: DiskFull #

What it means: The drive ran out of free space, so the save stopped. Existing saves were not changed, because the kit writes a temporary file first and only swaps it in once it is complete and checked.

Likely cause: The player's system drive, which holds AppData\LocalLow, is full or nearly full. Large uncompressed saves with many backups make this more likely.

Fix: Tell the player plainly, and let them try again. For example: "There isn't enough disk space to save. Free up some space and try again. Your previous save is safe." To make saves smaller, turn on File Options → Compress (JSON usually shrinks several times) or lower Backup Count. Check Success after your own save calls too. The kit's autosaves, including the one on quit, log their failures in the Console.

SK111: AccessDenied #

What it means: Windows did not let the kit write, or sometimes read, the save file or folder. Existing saves were not changed.

Likely cause: One of these:

  • The file or folder is marked read-only.
  • Another program has the file open, such as a text editor, a virus scan, or a backup or cloud-sync tool.
  • A second copy of the game is running.
  • Security software blocks the folder.

If the main file is locked during a load, the kit deliberately does not fall back to an older backup, because the newest save is probably fine.

Fix: Close the other program or the second copy of the game, and try again. In File Explorer, right-click the file or folder, choose Properties and untick Read-only. If security software blocks the game, the player needs to allow it. Tell the player their save is safe and that retrying usually works.

SK112: StorageUnavailable #

What it means: The kit could not reach the save folder at all, so nothing was read or written. Existing saves are not changed.

Likely cause: One of these:

  • SaveKit.Initialise() was called from a background thread. Unity then reports no persistent data path.
  • The folder is on a drive that was disconnected.
  • A cloud-sync tool still holds the file.
  • Windows reported a disk error the kit could not classify.

During a load, the kit does not fall back to an older backup for this code, because the newest save may be perfectly good.

Fix: Call SaveKit.Initialise() on the main thread, for example in Awake. Ask the player to reconnect the drive or wait for their sync tool to finish, then retry. The detail in brackets names the path the kit tried, which helps when a player sends you their Console output.

SK113: PathTooLong #

What it means: The full path of a save file is longer than Windows allows (usually 260 characters), so the file could not be written or read. Existing saves were not changed.

Likely cause: The parts of the path add up to too many characters. The path is C:\Users\<user name>\AppData\LocalLow\<Company Name>\<Product Name>, followed by Save Folder Name, Profile Folder, the file name patterns and File Options → File Extension. Long company, product or Windows user names make it worse.

Fix: Shorten Save Folder Name, Profile Folder and the file name patterns in the settings asset, and keep Company Name and Product Name reasonably short in Player Settings. Do this before you ship. After release, changing any of these names makes the kit look somewhere else, and existing saves seem to disappear (see SK100).

SK120: NewerVersion #

What it means: A newer build of the game wrote this save: its save version is higher than Save Version in this build. The kit refuses to load it rather than risk damaging it, and leaves the file untouched.

Likely cause: The player went back to an older build, for example through a beta branch, a rollback or an old installer. Saves may also have been copied from a machine with a newer build, or Save Version was lowered.

Fix: Never lower Save Version after release. Tell the player: "This save was made with a newer version of the game. Update the game to load it." Use SlotInfo.IsFromNewerVersion to mark these slots in your menu. Ask the player before overwriting. A save of only some categories into that slot is refused. A save of every category replaces the newer file, and keeps it as the newest backup only while Backup Count is above 0.

SK121: MigrationMissing #

What it means: The save has an older save version, and a step needed to upgrade it does not exist. The load was refused and the file was left untouched. The message names the missing version.

Likely cause: Save Version was raised without a step for every version in between. A step marked [SaveMigration(fromVersion: 3)] turns a version 3 save into version 4. A step can also be missing because:

  • It has the wrong shape. It must be static, take one SaveTree and return void. The Console warns when a step is ignored.
  • It sits in an Editor folder, so builds do not include it.
  • It sits in an assembly the kit treats as part of .NET, Mono, Unity or NUnit, and skips. Those are the assemblies named exactly System, mscorlib, netstandard, UnityEngine or UnityEditor, and every assembly whose name starts with System., Unity., UnityEngine., UnityEditor., Mono. or nunit.. The match is case-sensitive, and each prefix includes its dot, so a game assembly such as Systems.Gameplay, UnityExtras or MonoBehaviours.Core is still searched.
  • Auto Discover Migrations is off, and the step was not added with SaveKit.Migrations.Add.

Fix: Add the missing step, for example [SaveMigration(fromVersion: 3)] static void Upgrade3(SaveTree save) { ... }. Test it with a real save from that version. The player's file loads as soon as a build with the step ships.

SK122: MigrationFailed #

What it means: A migration step ran but threw an exception. Steps work on a copy of the save, so the file was left untouched and nothing was half-changed.

Likely cause: The step's own code failed. It may have expected a key or category that the old save does not have, converted a value to the wrong type, or used a Unity object or API. Steps run on a background thread together with the rest of the file work, so they may only edit the SaveTree.

Fix: The message names the step (Type.Method) and the exception. Make the step tolerant of missing data: check that save.FindPath(...) is not null before you use a value. Prefer the tree helpers RenameKeyEverywhere, RemoveKeyEverywhere, AddDefaultBeside and RenameCategory, which just do nothing when a key is missing. Test every step with real saves from the old version before you release it.

SK123: SaveVersionInvalid #

What it means: Save Version in the settings asset is not a whole number of 1 or more, so the kit refused to start. Nothing was read or written.

Likely cause: The field was set to 0 or a negative number, usually while experimenting with migrations or after resetting values by hand.

Fix: In the settings asset, under Game updates, set Save Version to 1 for a game that has never shipped. For a released game, set it back to the number your last release used. Then call SaveKit.Initialise() again. From then on, only ever raise it, by one each time your saved data changes shape, and add a [SaveMigration] step for each increase. Lowering it after release makes existing saves look newer than the game (SK120).

SK130: ObjectNotFound #

What it means: A saved object, link or parent points at something that is no longer in the scene, so that piece was skipped. The rest of the load succeeded. Skipped objects are listed in Report.SkippedObjects.

Likely cause: The object was deleted in a game update, or its Saveable was removed and added again, which gives it a new ID. A linked object or saved parent may be gone: the link becomes empty and the object stays where it is. An unsaved parent container may have been renamed: the object returns to the scene root, in the same world position. During a save, a field that links to a scene object without a Saveable is not saved. Links an ISaveable writes with SaveWriter.WriteObjectLink follow the same rules, and a warning names the value, such as Chest (ChestScript) (door).

Fix: If you removed the object on purpose, nothing is needed. Otherwise, restore it with its original Saveable from version control. Add a Saveable to every object your saved fields link to. Tools → All In One Save Kit → Diagnostics finds missing and duplicate IDs. Give unsaved containers unique names without /.

SK131: PrefabNotRegistered #

What it means: A runtime object spawned from a prefab could not be re-created on load, so the object and its state were skipped. Everything else loaded.

Likely cause: The prefab is not in the Prefab Registry: it was deleted, it lost the Saveable on its root, or the settings asset's Prefab Registry field is empty. SK131 also appears when your ISpawnHandler.Spawn returns null or spawns a prefab without a Saveable on its root. During a save, it means an object was copied at runtime from something that is not a prefab, so that object is not saved.

Fix: Run Tools → All In One Save Kit → Registries → Rebuild Registries, or run Diagnostics, which registers the prefab in one click. Check Prefab Registry under World in the settings asset. Put the Saveable on the prefab's root, spawn from the prefab asset, and make your spawn handler return the object it created. Fix this before players save again, because the next save records the world without the skipped objects.

SK132: AssetNotRegistered #

What it means: A saved link to an asset, such as a ScriptableObject item definition, could not be saved or restored. The asset is in neither the Asset Registry nor the Prefab Registry. That link is empty, and everything else saved or loaded normally.

Likely cause: One of these:

  • The asset was never registered. Assets are not added automatically the way prefabs are.
  • The settings asset's Asset Registry field is empty.
  • The asset was deleted or recreated, which gives it a new GUID.
  • The project was copied without its .meta files.

Fix: Run Tools → All In One Save Kit → Diagnostics. It finds ticked fields that point at unregistered assets and registers them in one click. Diagnostics cannot see assets that only your own ISaveable code writes: select them in the Project window and run Tools → All In One Save Kit → Registries → Register Selected Assets, or call RegistryUpkeep.RegisterAsset(registry, asset) from an editor script. Set Asset Registry under World in the settings asset. Renaming or moving a registered asset is safe. Keep .meta files in version control.

SK133: SceneNotRegistered #

What it means: A scene that holds saved objects is not in the Scene Registry. When saving, the kit stores that scene's objects under the scene's path instead of its permanent ID. When loading, a saved scene could not be found. Its state stays in memory and is applied if the scene loads later.

Likely cause: The settings asset's Scene Registry field is empty, or the registry was not updated after the scene was added. The scene may also have been deleted and created again, which gives it a new GUID. Scenes in Build Settings are registered automatically.

Fix: Run Tools → All In One Save Kit → Registries → Rebuild Registries, and set Scene Registry under World in the settings asset. Do this before you ship. A registered scene can be renamed or moved without breaking saves. Objects saved under a scene path are lost from the save if that path changes.

SK134: SceneNotInBuildSettings #

What it means: A scene that the save needs, or one passed to SaveKit.LoadScene, is not in Build Settings. In a build Unity cannot load it: the load carries on without that scene, and its saved state stays in memory and is applied if the scene loads later. In the Editor the kit loads it straight from the project anyway and warns once per scene, because a build could not. When a saved scene cannot be loaded but is open already, its saved state is restored into the open scene, with this warning: in the Editor, an open scene with the same id, or with the same name when it has no file of its own; in a build, only an open scene with the same id, and never for the first saved scene, which decides the scenes that stay open.

Likely cause: The scene was never added to the build's scene list, or it was removed from it. Or your game loads the scene some other way, such as Addressables or asset bundles, that the kit does not know about.

Fix: Add the scene to the build's scene list. In Unity 6, use File → Build Profiles (Scene List). In Unity 2022.3, use File → Build Settings. Tools → All In One Save Kit → Diagnostics finds these scenes and adds them in one click. If your game loads scenes its own way, set SaveKit.World.SceneLoader to your own ISceneLoader, or set World Load Mode to Restore Into Current Scenes.

SK140: HostOnly #

What it means: This copy of the game is a co-op client, and only the host or a solo player may save, load or delete world saves. The call was refused, and no file was touched.

Likely cause: SaveKit.Authority is set, and its HasSaveAuthority returned false. On this machine, the kit then refuses slot saves, loads and deletes, autosaves, the quicksave, and SaveKit.RestoreBackup. If HasSaveAuthority throws an exception, the kit also refuses, and says why in the Console.

Fix: This behaviour is by design. Check SaveKit.CanSave and SaveKit.CanLoad before you show a save or load button of your own; both are false on a client. The kit's save menu does this itself: a client sees the slot cards without their Save, Load, Delete and Restore backup buttons, and a line saying only the host can save. Let the host save. Make sure your authority returns true on the host. For a solo game, leave SaveKit.Authority null, which always allows saving. Clients can still keep their own settings with SaveKit.SaveGlobal() and SaveKit.LoadGlobal(). The quit autosave does this for clients automatically.

SK141: PlayerUnknown #

What it means: The kit could not match a connected player to a stable player ID, so it cannot find that player's saved data, and the player starts from defaults.

Likely cause: SaveKit.Players.ForConnection(connectionId) returned null and wrote SK141 to the Console, once per connection, for one of these reasons:

  • No IPlayerIdentity is set: SaveKit.Identity is null.
  • Your IPlayerIdentity.TryGetPlayerId returned false, or an empty ID, for that connection.
  • Your TryGetPlayerId threw an exception. SaveKit.Players.TryGetPlayerId reports this case too; it is otherwise the quiet form, for code that asks again later.

A player the save has never seen is not this code: SaveKit.Players.For(id) gives them empty data, and every Get returns the default value you pass.

Fix: Set SaveKit.Identity to your identity before players connect. Make TryGetPlayerId return false instead of throwing while a player's stable ID is not known yet, for example before their Steam ID arrives, and ask again later with SaveKit.Players.TryGetPlayerId, which stays quiet. Use an ID that stays the same every session, never the network connection number, which changes each time. Use SaveKit.Players.Has(id) to tell a returning player from a new one.

SK150: CategoryUnknown #

What it means: A category name was used that the settings asset does not define. Category names must match exactly, including capital letters.

Likely cause: A typo, such as "progress" instead of "Progress". Look in SaveKit.Data.Set, in the categories passed to Save or Load, and in each Saveable's category. A category may also have been renamed or removed. Initialise also fails with SK150 in these cases:

  • No categories exist.
  • Default Category is not in the list.
  • World Category is not in the list.

Fix: Add the category on the settings asset's Advanced tab, under Categories, or fix the spelling. A save or load that names an unknown category is refused before anything is written. Values set in an unknown category, and Saveables that use one, are never saved. The Console warns once for each unknown name.

SK151: SlotOutOfRange #

What it means: The slot number is outside the range the game offers. Slots are numbered from 1 up to Slot Count in the settings asset. Nothing was read or written.

Likely cause: One of these:

  • Slot 0 was used. Slots start at 1, not 0.
  • A menu's list index was passed without adding 1.
  • Slot Count was lowered in an update, so the higher slots no longer exist.

Fix: Pass a number from 1 to SaveKit.Settings.SlotCount. If you lowered Slot Count (1 to 99) after release, raise it again. Files in the higher slots are still on disk. The kit just does not touch them while they are out of range.

SK152: SlotEmpty #

What it means: The slot has nothing saved in it yet: no main file, temporary file or backup. SlotInfo.Status also reports SK152 for empty slots shown in a menu. Nothing was changed.

Likely cause: SaveKit.Load(slot) was called on a slot the player never saved to, or on one they deleted. If slots that used to hold saves are suddenly empty, the kit is probably looking in a different folder or for different file names (see SK100).

Fix: Before you offer Load, check SaveKit.HasSave(slot), or read SaveKit.GetSlotInfo(slot).Exists when you draw the menu. For empty slots, offer New Game or Save instead.

SK153: SettingsInvalid #

What it means: A value in the settings asset cannot be used, so the kit refused to start. Nothing was read or written. The message names the field and the problem.

Likely cause: One of these:

  • Slot File Name Format or Autosave File Name Format has no {0} in it, so every slot would write the same file; its braces are broken, as in slot_{0 or slot_{0:00; or it uses another placeholder such as {1}.
  • Profile Folder holds {profile}, but SaveKit.ProfileId was empty when the kit started, so the kit could not tell whose saves to use. With Initialise Automatically ticked, this shows up as the kit failing to start by itself.
  • SaveKit.ProfileId holds a character a folder name cannot hold, such as /, \, : or ...
  • A category is called players. The kit keeps each co-op player's own data under that name in every save, so a category with the same name would overwrite it.
  • Use Slot Options For Global File is unticked and Global File Options → File Extension cannot be used: it needs a dot and a few letters, and it cannot be .tmp, start with .bak or .corrupt, which the kit uses for its own copies.

Fix: Use a file name pattern with {0} where the number goes. For example, slot_{0:00} gives slot_01, and autosave_{0} gives autosave_1; or leave the field empty to use the default. Change these patterns only before release, because after release the kit would look for saves under the new names (see SK100). For a profile folder with {profile}, untick Initialise Automatically, set SaveKit.ProfileId (for example to the player's Steam ID) and then call SaveKit.Initialise(). Rename a category called players, for example to PlayerProgress. Give the global file an extension such as .local, or leave it empty to keep the slots' extension. Then call SaveKit.Initialise() again.

SK154: LoadInProgress #

What it means: A slot save, autosave, quicksave or SaveKit.RestoreBackup was requested while SaveKit.LoadAsync was still loading the scenes its save was made in. Saving or restoring at that moment would write over the save that was just loaded while the world is only half restored, so nothing was written.

Likely cause: Game code saved during a load. For example, the player pressed a save button, or a script saved straight after starting LoadAsync without awaiting it. The kit's own timer and scene-change autosaves wait for the load to finish. The autosave on quit is skipped during a load, with a Console warning.

Fix: Before saving, await SaveKit.LoadAsync(...) or wait for the SaveEvents.Loaded event. Disable save buttons while a load runs, then save again once it has finished. Saving the global file with SaveKit.SaveGlobal() is still allowed during a load, so player settings are never blocked.

Still stuck? #

Report a bug with the bug report form, ask a question in Discussions, email marklromano@outlook.com or visit https://marklromano.github.io/.

Get help: Discord https://discord.gg/AmpBDxRAKu · bug tracker https://github.com/marklromano/RomanoAssetSupport · website https://marklromano.github.io/ · e-mail marklromano@outlook.com. With a question or a bug, please paste your system info: in Unity, Tools → All In One Save Kit → Start → Help and support → Copy system info. To get an answer quickly, please send:

  1. The Console report. Include every line that starts with [All In One Save Kit] from around the time of the problem, with any stack trace. If you can reproduce the problem, set Log Level to Verbose first.
  2. The save file. Use Tools → All In One Save Kit → Save Inspector to export the save. For a damaged save, zip the raw files from the save folder instead, including any .bak, .tmp and .corrupt- copies. The Save Inspector can open that folder for you.
  3. Your Unity version (Help → About Unity) and platform: Windows 10 or 11, and whether it happened in the Editor, a Mono build or an IL2CPP build.
  4. The SK code and what you were doing when it appeared.

Support covers bugs in the kit and questions about setting it up. It does not include reviewing or debugging your own game code. A stack trace usually shows which side a problem is on: one that ends in your script points at your code, and one inside AllInOneSaveKit points at the kit.
