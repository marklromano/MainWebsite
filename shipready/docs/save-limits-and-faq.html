Docs/Shipready/Saves

Limits and FAQ

This page lists what Shipready does not do, where its limits are, and which platforms and Unity versions it supports. It ends with answers to the questions buyers ask most.

Settings in bold, such as Save Version, are fields on the settings asset ShipreadySaveSettings. Select it in the Project window to change them.

What Shipready does not promise #

  • It does not save any object automatically. It saves plain data and the supported Unity state listed on this page. Anything else needs a short script, and the Inspector says so clearly: the Field Picker greys out fields it cannot save and shows the reason.
  • It is not anti-cheat. Encryption stops casual save editing, not a determined player.
  • There is no cloud sync in 1.0. You get a step-by-step Steam Cloud guide instead (SteamCloud.md).
  • Platforms are limited at launch. There is no support for macOS, iOS, Android, WebGL or consoles in 1.0.
  • There is no mid-session co-op loading. The host loads a save before friends join.
  • Some engine state is not captured. This includes particle systems, physics joints, running coroutines, and the exact path of a NavMesh agent (the NavMesh Agent saver brings back its position and destination, and it works the path out again). An Animator mid-blend is saved as the state it is blending into. Games rebuild the rest on load from their own saved values.

"Save Data in code" means one line such as SaveKit.Data.Set("gold", gold, "Progress");, read back with SaveKit.Data.Get("gold", 0, "Progress").

Which values can be saved #

  • Built in:
  • numbers, text, true/false, dates, durations, GUIDs and byte arrays
  • enums, stored by name, so reordering an enum never breaks a save
  • Vector2, Vector3, Vector4, Vector2Int, Vector3Int, Quaternion, Color, Color32, Rect, RectInt, Bounds and BoundsInt
  • lists and arrays of all of the above
  • Dictionary<string, T> and Dictionary<int, T> of any of the above, through SaveKit.Data.Set and Get, or SaveWriter.WriteDictionary, SaveReader.ReadDictionary and SaveReader.ReadIntDictionary. Any other dictionary is not saved, with an SK002 warning in the Console.
  • Your own [Serializable] classes and structs are saved under Unity's own rules, through Unity's JsonUtility. If the Inspector shows a value, Shipready can save it.
  • References: to other saved objects by their ID, and to registered assets (ScriptableObjects and prefabs) by their asset ID, from ticked fields or from an ISaveable with WriteObjectLink.
  • Numbers are exact. Floats and doubles read back bit for bit, and a readable save shows them in their shortest exact form, so 0.8f is written as 0.8.

The Field Picker only offers fields Unity itself saves: public fields, or fields marked [SerializeField], of a supported type. It cannot save static, read-only, [NonSerialized] or [SerializeReference] fields, interfaces, delegates, nullable values, multi-dimensional arrays, or lists of lists. Save those from an ISaveable instead.

The limits of encryption #

Encryption is off by default. Switch it on with File Options → Encrypt.

  • The key ships inside your game. The passphrase is stored in the settings asset, which is part of your build. A determined player can dig it out of the game files. Mono builds are especially easy to decompile, and IL2CPP only makes this harder.
  • It stops casual editing. A player cannot change an encrypted save in a text editor. If one byte changes, the tamper check notices, and Shipready loads the newest backup instead (see SK105).
  • It is not anti-cheat. In co-op, the host's save is the authority anyway.
  • Never use it for passwords, payment details or other personal data. Never use it for anything a server should check.
  • The slot info stays readable. Name, date, playtime, location and summary lines stay readable by default, so the menu never has to decrypt a whole save. Switch on File Options → Encrypt Slot Info to encrypt them too.
  • Thumbnails are never encrypted. They are plain PNG files next to the save.
  • Choose your own passphrase before release. Diagnostics warns while the default passphrase is still set. After release, never change Passphrase, Key Salt or Key Iterations, or existing encrypted saves can no longer be opened (see SK106).

How it works, for programmers: AES-256-CBC with a random IV for every write, and HMAC-SHA256 over the header and the encrypted data (encrypt-then-MAC). The keys are derived from your passphrase with PBKDF2, once, when Shipready starts. Data is compressed before it is encrypted, and each file records which options it was written with, so changing these settings in an update never strands old saves (see GameUpdates.md).

Steam Deck Not separately tested. Windows builds normally run there through Proton.
macOS and iOS Not supported

Consoles Not supported. You can plug in your own storage: implement ISaveStorage and pass it to SaveKit.Initialise(settings, storage).

Unity versions #

Shipready is supported from Unity 2022.3 LTS, and tested on Unity 6.3 LTS and the newest Unity 6 release.

Unity version Status
2022.3 LTS Supported: the minimum version. Not tested separately.
6.3 LTS Supported and tested
The newest Unity 6 release Supported and tested. The co-op sample was tested here.
6.0 LTS and other 6.x versions Supported, but not tested separately
  • The co-op sample needs Unity 6 and Netcode for GameObjects 2.x. Its scripts compile only when NGO 2.x is installed, so they stay out of the way in Unity 2022.3 and in projects without NGO. A menu command builds the sample scene once NGO is installed. It was tested with NGO 2.13.3 on Unity 6000.6.
  • Render pipelines: Built-in, URP and HDRP. The core has no rendering code. Demos are checked in Built-in and URP; HDRP gets automated tests only. The demo scenes pick materials for the active pipeline when they run.
  • Scripting backends: Mono and IL2CPP.
  • Input: the Input Manager, the Input System, or both. The player menu works with either.
  • Dependencies: none outside Unity. The player menu, the editor tools' windows and the demos use uGUI and TextMeshPro (in Unity 2022.3, TextMeshPro is a separate Unity package). The runtime and the core editor services (saved ids, the registries and the migration link file) need neither and keep working without them. The Asset Store installs the two packages together with Shipready when the publisher declares them as dependencies; otherwise Tools → Shipready → Saves → Required Packages explains how to install them in the Package Manager; Shipready never installs packages itself. See Required Unity packages.

Known limits #

Data and files #

  • Dates are stored as UTC. A DateTime whose Kind is Local or Unspecified is converted to UTC when it is saved. It comes back as the same moment in UTC, with Kind set to Utc, not as the same clock reading. Call .ToLocalTime() before you show it to a player. Unspecified is treated as local time.
  • Data can be nested at most 128 levels deep. A save nested deeper is refused before anything is written (see SK002).
  • Automatic Fallback off, and a crash on a slot's very first save. With File Options → Automatic Fallback off, a crash during the very first save of a slot, before the new file was swapped into place, leaves only slot_01.save.tmp. Loading that slot reports SK101, and the menu's Restore backup button (or SaveKit.RestoreBackup(slot)) puts the .tmp file in place.
  • The global file always falls back. The global file holds the player's settings and has no slot card to restore it from. It therefore loads its newest valid backup whatever Automatic Fallback says.
  • One global file. Every Global category goes into the same global file. It can have its own options and extension, for example .local to keep it out of Steam Cloud, but you cannot split Global categories between a synced file and a local one.
  • Changing the global file's own extension. When a game update gives the global file its own extension, or takes it away again, Shipready loads whichever of the two files was written last, so players keep their settings. Changing the global file's own extension from one value to another, such as from .local to .cfg, leaves the settings under the old name behind.
  • Profile folders need the player's ID before Shipready starts. With {profile} in Profile Folder, Shipready refuses to start until your game sets SaveKit.ProfileId (SK153). Switch Initialise Automatically off and start Shipready yourself once the ID is known, or set the ID in a RuntimeInitializeLoadType.AfterAssembliesLoaded method. Shipready reads the ID only when it starts.
  • A category cannot be called players. That name holds each co-op player's data in every save, so Shipready refuses to start with such a category (SK153).
  • Migration steps in assemblies named like Unity's or .NET's are not found. When Shipready looks for [SaveMigration] steps, it skips the assemblies System, mscorlib, netstandard, UnityEngine and UnityEditor, and every assembly whose name starts with System., Unity., UnityEngine., UnityEditor., Mono. or nunit.. A game assembly such as Systems.Gameplay or UnityExtras is searched (see GameUpdates.md).

World persistence #

  • Links to objects in other scenes. A link to an object in another scene comes back only when that object is awake, or when its scene is part of the same load. Otherwise the link stays empty, with a warning.
  • Parent paths. A runtime object under a parent that is not saved remembers that parent by its path in the hierarchy. The path assumes that sibling names are unique and contain no /. If the parent cannot be found, the object returns to the scene root in the same world position (see SK130).
  • Physics release timing. Restored rigidbodies are held kinematic through one physics step, then released with their own settings, velocities and sleep state, so stacked objects do not burst apart. The release follows FixedUpdate. If Physics.simulationMode is set to Update or Script, the release may not line up with your simulation step.
  • Inactive runtime copies. If you copy a scene object with Instantiate during play and the copy stays inactive, it keeps the original's ID until it is activated for the first time. Activate such copies before the next save, or spawn them from a prefab instead.
  • Destruction is recorded only during gameplay. A Saveable records that it was destroyed only while the game runs. It records nothing when its scene unloads or the game quits.
  • Your own scene loading. SaveKit.LoadScene and SaveKit.UnloadScene remember a scene's state when the player leaves it. If you unload scenes yourself, call SaveKit.World.CaptureScene(scene) first. Scenes loaded through Addressables or asset bundles need your own ISceneLoader (see SK134).
  • SaveKit.NewGame resets Shipready's data, not your scene. Objects in the scenes that are open keep whatever state they have, and the next slot save or quicksave captures them as they are. Load the first scene of the new game, or put the open scene's objects back to their new-game state yourself.
  • Leaving a scene a new game started in. The scenes that are open when NewGame is called are marked. A slot save, a quicksave or your own SaveKit.Autosave() call captures them and clears the mark. Until then, Shipready's own autosaves (timer, scene change, and quit or pause) leave them out, so an autosave never writes the old game's objects into the new game's save, and leaving such a scene does not capture it into scene memory. A new game that starts in the open scene should make a slot save or a quicksave before the player leaves it, or that scene's changes since NewGame are not remembered when the player returns.

Player menu #

  • Thumbnails are not rotated with backups. After a backup is restored or loaded, the slot card still shows the picture of the newer, damaged save. The next save to that slot writes a new picture, or removes the old one.
  • A save without a picture has no thumbnail. A slot save, autosave or quicksave made without a picture removes the thumbnail of the save it replaced, so the card shows "No preview" rather than an older picture. The menu takes a picture before every save it makes, while its Take a picture for each save is on and there is a camera, and every slot save, autosave and quicksave takes one from the main camera while Capture Autosave Thumbnails is on, so slot saves from your own code get pictures too; SaveKit.SetNextThumbnail sets your own instead (see "Thumbnails" in the Manual). Without a camera or a graphics device, and for the suspend autosave of a phone or handheld, there is no picture.
  • Load Saved Scenes mode. In the default World Load Mode, Load Saved Scenes, a load replaces the loaded scenes. If you need the menu's LoadFinished event, put the menu in a scene that stays loaded, or under DontDestroyOnLoad.

Co-op #

  • Only the host saves and loads world data. A client that tries gets HostOnly (see SK140). Clients keep their own settings file.
  • Shipready restores state on the host only. Getting that state to clients is the network library's job, so values clients must see have to be synced by your game, for example with NetworkVariables.
  • Only Netcode for GameObjects is shown. The core works with any networking library through the co-op hooks, but the sample uses NGO 2.x only, and was tested with NGO 2.13.3.
  • A dropped connection lingers in the sample. A player whose connection dropped stays in the game until Unity Transport's disconnect timeout, 30 seconds by default, and cannot rejoin under the same ID until then.

FAQ #

Where are my saves? #

On Windows, saves are kept here:

%USERPROFILE%\AppData\LocalLow\<Company Name>\<Product Name>\Saves
  • Company Name and Product Name come from Project Settings → Player.
  • Saves is Save Folder Name. If Profile Folder is set, the saves are in that folder inside it. {profile} in Profile Folder is replaced by SaveKit.ProfileId, such as the player's Steam ID, so each player's saves are in Saves/<their ID>.
  • In the Editor and in a Windows build, the folder is the same.
  • Slot 1 is slot_01.save. The global file, which holds the Settings category, is global.save, or global.local if you gave it its own extension.

Tools → Shipready → Saves → Save Inspector lists every save and can open the folder. In code, SaveKit.Storage.DescribeLocation() returns the path once Shipready has started.

Do I need code to start Shipready? #

No. With Initialise Automatically on, which is the default, Shipready starts by itself just before the first scene loads, in the Editor and in builds, using the settings asset the Setup Wizard made. Switch it off and call SaveKit.Initialise() yourself only when Shipready has to wait for something, such as the player's Steam ID for a profile folder. See "Starting Shipready in your game" in the Manual.

Can players edit saves? #

By default, saves are readable JSON. They are indented in the Editor and in development builds, and compact in release builds.

  • An edited save counts as damaged. If a player changes a value in a text editor, the file no longer matches its checksum. In a build, Shipready then loads the newest backup and keeps the edited file as .corrupt-<time> (see SK104). Changes to spacing alone do not count.
  • The Editor always accepts edits. It loads edited files with a warning, so you can tweak saves while you test.
  • To let players edit saves, for example for modding, set File Options → Checksum Policy to Accept With Warning.
  • To stop casual editing, switch on File Options → Encrypt and set your own passphrase. Remember that encryption is not anti-cheat.

What happens if the game crashes mid-save? #

Nothing is lost. Each save:

  1. writes a temporary file,
  2. reads it back to check it, and
  3. only then swaps it into place, using Windows' atomic replace.

At every moment, at least one complete copy is on disk. The next load tries the main file first, then a complete temporary file, then each backup, newest first. Shipready's own tests cut saves short after every step, hundreds of times, and the next load always found a complete copy. The autosave on quit waits until its file is safely written.

Does loading a slot overwrite my settings? #

No. Categories marked Global, which by default means Settings, live in the global file, not in the slots. Loading a slot loads only Slot categories. Shipready loads the global file by itself when it starts. A slot save also writes the global file when the game holds global values, but a load never takes them back.

To save settings on their own, call SaveKit.SaveGlobal().

How do I start a new game? #

Call SaveKit.NewGame(), then load your first scene:

using RareGeometry.Shipready.Save;
using UnityEngine;

public class MainMenu : MonoBehaviour
{
    public void StartNewGame()
    {
        // Every Slot category is emptied, and scene memory, players and playtime start again.
        // Global categories, such as the player's settings, are kept. Nothing on disk changes.
        SaveKit.NewGame();
        SaveKit.LoadScene("Level1");
    }
}

Without NewGame, values from the last loaded game stay in memory. A later save into an old slot would also keep that slot's categories that the new game has not written yet. With NewGame, the next save replaces them.

NewGame resets Shipready's data, not the objects in your scenes. To start the new game in the scene that is already open, call NewGame and put that scene's objects, and your own values, back to their new-game state yourself; reloading the scene is often the simplest way. The next slot save or quicksave captures the scene as it is then; Shipready's own autosaves leave it out until that first save. Make that save before the player leaves the scene, so its state is remembered when they come back.

Can I save at any time in co-op? #

  • The host can. The host, or a solo player, can save at any time. The one exception is while SaveKit.LoadAsync is still loading scenes (see SK154).
  • Clients cannot. They get HostOnly, and Shipready's save menu hides the Save, Load, Delete and Restore backup buttons for them. Check SaveKit.CanSave before you show save buttons of your own.
  • Loading happens before friends join. 1.0 has no mid-session co-op loading.
  • Clients keep their own settings. They can still save their own settings file with SaveKit.SaveGlobal().

Will old saves still load after I update my game? #

Yes, if you plan for it. Raise Save Version when your saved data changes, and write a small migration step. Most changes, such as adding values or objects, need no step at all. See GameUpdates.md.

Can I change compression or encryption after release? #

Yes. Each file records how it was written, so old files keep loading. Do not change Passphrase, Key Salt or Key Iterations after release. See GameUpdates.md.

Does it work with Steam Cloud? #

Yes, through Steam's code-free Auto-Cloud. Shipready names its files so that one pattern, *.save, uploads only the real saves. A Profile Folder of {profile}, with SaveKit.ProfileId set to the player's Steam ID, keeps two Steam users on one PC apart, and giving the global file its own extension, such as .local, keeps machine-specific settings on the PC. See SteamCloud.md.

Something went wrong. Where do I look? #

Every result carries a code such as SK101, a plain-English message and a link to its entry in Troubleshooting.md. Always check result.Success after your own save and load calls.

What does support cover? #

Support covers bugs in Shipready and questions about setting it up. It does not cover reviewing or debugging your own game code. A stack trace usually shows which side a problem is on: one that ends in your script points at your code, and one inside RareGeometry.Shipready.Save points at Shipready. The end of Troubleshooting.md lists what to send so that you get a quick answer.

Contact #

Report a bug with the bug report form, ask a question in Discussions, email the address in Tools > Shipready > Saves > Help or visit https://raregeometry.github.io/.
