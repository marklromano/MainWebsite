Using it in an existing game

The Quick Start is the fastest route in a new project. In a game you've already built, Shipready has to share the input, cursor, pause, UI, audio and post effects your game already owns. This page says what Shipready does with each one, what you may see, and how to fix it. Shipready never takes over one of your systems unless you ask it to.

Before you start: commit or back up your project, then run the menu builder's Check tab after adding the front end. It lists extra EventSystems, settings that nothing listens to yet and a missing mixer, each with a Fix button.

Input #

You use a PlayerInput component (one player). Nothing to do: set the Key Bindings setting's Actions to the same Input Action Asset your PlayerInput uses. A single PlayerInput uses that asset itself, so rebinds reach your player straight away.

You use a generated C# class (controls = new MyControls()). That class makes its own copy of your actions, so the menu's rebinds wouldn't reach it on their own. Register the copy once:

using RareGeometry.Shipready.Settings.Rebinding;

controls = new MyControls();
InputBindings.Track(controls.asset);    // follows rebinds and look sensitivity from now on
// when you dispose it: InputBindings.Untrack(controls.asset);

Local multiplayer (PlayerInputManager). Every player after the first gets a copy of the actions. Add Player Input Bindings Sync (Add Component > Rare Geometry > Settings Menu) next to the PlayerInput on your player prefab.

Symptom: "My new key shows in the menu, but the character still uses the old one." The game reads a copy of the actions: use one of the two fixes above.

Turning off player input while a menu is open. Shipready doesn't disable your PlayerInput (that can change device pairing). It raises the input lock: MenuRoot.InputLockChanged (static), onInputLockChanged (UnityEvent) and MenuRoot.Instance.InputLocked. Switch your action map or ignore input there:

void OnEnable() => MenuRoot.InputLockChanged += OnLock;
void OnDisable() => MenuRoot.InputLockChanged -= OnLock;
void OnLock(bool locked) { if (locked) playerInput.SwitchCurrentActionMap("UI"); else playerInput.SwitchCurrentActionMap("Player"); }

Old Input Manager. Menus, Esc / Start and gamepad navigation work. Key rebinding and button prompts need the Input System package.

Mouse cursor (first-person and third-person games) #

Release Cursor In Menus (front end > Menu Root, on by default): while any menu shows, the cursor is unlocked and visible; when the menus close, it goes back exactly as your game had it. If your controller locks the cursor every frame, Shipready still wins while a menu is open (it runs after your Update), but it's cleaner to stop locking while MenuRoot.Instance.InputLocked is true. Turn the switch off when your game has its own cursor manager.

Pause and time scale #

  • Freeze sets Time.timeScale to 0 and restores the value it had. If your game changes the time scale while paused (slow motion ending, hit-stop), your newer value is kept.
  • Your own pause menu stays yours: set Pause Mode to Custom (only the onPaused / onResumed events) or turn off the Pause screen and keep Pause Without Screen on to use Shipready's time, audio and input lock with your UI.
  • Menus, countdowns and transitions use unscaled time, so they run while the game is frozen. Menu sounds and music ignore AudioListener.pause.

Your UI and EventSystem #

  • EventSystem: if your scene has one, Shipready uses it and doesn't add another. It only creates one when there is none. The Check tab finds duplicates and wrong input modules.
  • Draw order: the front end is a Screen Space Overlay canvas with Sort Order 100. If your HUD or dialogs use a higher order, raise the front end's Canvas > Sort Order so menus draw above them.
  • Keep your own menus: put Menu Button components on your own buttons to open Shipready's Settings or Credits, pause, resume or go back to the main menu (MenuRoot.Instance.OpenScreen("...") opens any screen by name), and turn off Shipready screens you don't need (Setup tab > Screens). Settings work without any kit UI at all: SettingsRuntime.Current.GetFloat("audio.music-volume").

Saves #

Continue, Load Game and Save Game follow your save system once you set MenuRoot.Instance.SaveBridge (see Extending and API). Without one, the buttons raise onNewGame, onContinue and onLoadGame and Continue shows after SetHasSave(true). Settings are stored apart from your saves (or in your own storage through ISettingsStorage).

Audio #

  • No mixer: Master Volume works through AudioListener.volume; the other volume sliders stay hidden until a mixer is assigned.
  • Your own mixer: expose each group's volume and type its exact parameter name into the matching volume setting. A wrong name logs a warning that names the setting and the mixer.
  • Your AudioSources must output to the right mixer groups for Music, Effects and Voice to change anything.

Post effects and graphics (URP, HDRP, Post Processing v2) #

  • Your Volumes and profiles are never edited. Shipready adds its own global Volume (priority 1000, Default layer) with a runtime profile. When an effect is On, your own Volumes stay in charge; only Off adds an override. Brightness, while it isn't at 0, sets Post Exposure (and nothing else of your Color Adjustments).
  • If your camera's Volume Mask leaves out the Default layer, Shipready's post settings can't reach that camera: add Default to the mask, or hide those settings.
  • Your URP asset file is never changed; render scale, MSAA, HDR and shadows go to a runtime copy.

Scenes #

  • One persistent front end: it lives across scene loads (Don't Destroy On Load). A second front end in a later scene removes itself, so you can put one in every scene you test from.
  • Bootstrap scene: put the front end in your bootstrap scene, then mark each scene with Menu Scene Mode (Front End, Gameplay or Hidden).
  • Additive scenes: put Menu Scene Mode only in the scene that decides the mode, not in every additive scene.
  • Your own scene loading (Addressables, a scene manager): leave New Game Scene empty and load from the onNewGame event, then call MenuRoot.Instance.EnterGameplay().
  • One-scene games: call EnterGameplay() when play starts and ShowFrontEnd() to go back (the Try It sample works this way).

Multiplayer #

Settings stay on each player's machine. Use Overlay Only pause so a networked game keeps running, and turn off Pause On Controller Disconnect for online games. The input lock is one switch for the whole machine; for split screen, decide per player in your own input code.

Five-minute check #

  1. Press Play in a level scene and press Esc / Start: the pause menu opens, the cursor is free, the game stops.
  2. Rebind Jump, Apply, resume: the new key jumps. Stop and start Play again: it's still rebound.
  3. Move Music Volume: the music changes.
  4. Turn Bloom off: it's gone; turn it on: your own look is back.
  5. Resume: the cursor locks again and your controls work.

Something different? Kit window > About > Copy system info, and post it in Support.
